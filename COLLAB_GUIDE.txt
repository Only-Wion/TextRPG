================================================================
TextRPG 项目 GitHub 协作指南（两人小团队新手版）
================================================================

本文件面向零开发经验的两人团队，帮助你们在 TextRPG 项目中
顺畅地使用 GitHub 进行协作。内容力求简洁、可直接复制粘贴。

----------------------------------------------------------------
第一部分：专业术语解释（简洁版）
----------------------------------------------------------------

repo / repository（仓库）
    存放项目所有文件和历史记录的地方。TextRPG 的仓库地址就是
    https://github.com/Only-Wion/TextRPG。

branch（分支）
    仓库的一条独立开发线。默认分支叫 main，你可以从 main 拉出
    新分支来开发功能，互不干扰。

commit（提交）
    把当前的文件改动"存档"到本地历史记录里。每次 commit 都附带
    一条描述信息，方便日后查看改了什么。

issue（议题）
    在 GitHub 网页端创建的任务卡片，用于记录 bug、功能需求或讨论。
    每个 issue 都有编号，例如 #12。

pull request / PR（拉取请求）
    把你的分支上的改动"申请合并"到 main 分支。PR 是代码审查的
    核心入口，队友可以在这里评论、提意见。

review（代码审查）
    队友查看 PR 里的改动，确认没有问题后点击 Approve（批准），
    或者提出修改意见（Request changes）。

merge（合并）
    PR 通过审查后，把分支上的改动正式并入 main 分支。

clone（克隆）
    把远程仓库完整下载到本地，包含所有文件和历史记录。
    克隆之后才能在本机编辑代码。

fork（派生）【可选了解】
    在自己账号下复制一份别人的仓库。适合给外部项目贡献代码。
    两人同属同一仓库时一般不需要 fork，直接创建分支即可。

CI（持续集成，Continuous Integration）
    每次推送代码或提交 PR，GitHub 会自动运行预设的检查脚本
    （如测试、代码风格检查）。CI 全部通过才建议合并，确保
    main 分支始终可运行。


----------------------------------------------------------------
第二部分：Git / GitHub 常用命令合集
----------------------------------------------------------------

【说明】
- 以下命令在本地终端（命令行）中执行，以 git 开头。
- GitHub 网页端操作（创建 Issue、提 PR、Review、Merge）
  不在命令行完成，直接在浏览器里点击即可。
- 首次使用前需配置用户名和邮箱（只需做一次）：
    git config --global user.name "你的名字"
    git config --global user.email "你的邮箱"

──────────────────────────────────────────────────────────────
克隆仓库（首次下载到本地）
──────────────────────────────────────────────────────────────
    git clone https://github.com/Only-Wion/TextRPG.git

执行后会在当前目录生成 TextRPG 文件夹，包含完整项目。

──────────────────────────────────────────────────────────────
查看当前状态（最常用，没事就跑一下）
──────────────────────────────────────────────────────────────
    git status

显示哪些文件被修改、哪些已暂存、当前在哪个分支。

──────────────────────────────────────────────────────────────
拉取远端最新代码（保持本地与 main 同步）
──────────────────────────────────────────────────────────────
    git pull origin main

在开始新工作或切换分支前，先执行这条命令更新本地代码。

──────────────────────────────────────────────────────────────
创建并切换到新分支
──────────────────────────────────────────────────────────────
    git checkout -b fix/help-command-typo

分支名建议用小写 + 连字符，前缀可用 fix/（修复）或 feat/（新功能）。

切换到已有分支：
    git checkout main

查看所有本地分支：
    git branch

──────────────────────────────────────────────────────────────
暂存文件并提交
──────────────────────────────────────────────────────────────
    git add <文件名>          # 暂存指定文件
    git add .                 # 暂存全部改动（当前目录）
    git commit -m "fix: 修正 help 指令的描述文字"

commit 信息写清楚"做了什么"，方便队友和日后的自己阅读。

──────────────────────────────────────────────────────────────
推送分支到远端
──────────────────────────────────────────────────────────────
    git push origin fix/help-command-typo

首次推送新分支时，GitHub 会提示你去创建 PR，复制链接在浏览器打开即可。

──────────────────────────────────────────────────────────────
Rebase（基础用法：把 main 的新提交同步到自己的分支）
──────────────────────────────────────────────────────────────
    git checkout fix/help-command-typo   # 切到自己的分支
    git fetch origin                     # 从远端获取最新信息
    git rebase origin/main               # 把 main 的新提交"垫"在自己改动之前

如果 rebase 过程中出现冲突，按下面"解决冲突"的步骤处理，
处理完后执行：
    git rebase --continue

如果搞乱了想放弃 rebase：
    git rebase --abort

──────────────────────────────────────────────────────────────
解决冲突的基本流程
──────────────────────────────────────────────────────────────
1. 执行 git status，找到显示 "both modified" 的文件。
2. 用编辑器打开冲突文件，找到 <<<<<<< / ======= / >>>>>>> 标记。
3. 手动选择保留哪段内容，删掉冲突标记。
4. git add <已解决的文件>
5. git rebase --continue（或 git commit，如果是 merge 冲突）

【小提示】遇到冲突不要慌，先截图给队友看，一起决定保留哪个版本。

──────────────────────────────────────────────────────────────
查看提交日志
──────────────────────────────────────────────────────────────
    git log --oneline --graph --decorate -20

以简洁方式显示最近 20 条提交记录。

──────────────────────────────────────────────────────────────
回退到某次提交（⚠️ 请先阅读安全提醒）
──────────────────────────────────────────────────────────────
【安全查看，不改动任何文件】
    git checkout <commit-SHA>       # 进入"游览"模式，只读

【撤销本地未推送的提交（安全）】
    git revert <commit-SHA>         # 生成一个"反向提交"，不修改历史

【强制回退（危险！已推送则会污染远端历史，谨慎使用）】
    git reset --hard <commit-SHA>

⚠️ 安全提醒：已推送到 GitHub 的提交不要用 reset --hard，
   用 git revert 代替，这样队友的本地仓库不会出问题。

──────────────────────────────────────────────────────────────
从远端拉取别人的 PR 分支（可选）
──────────────────────────────────────────────────────────────
    git fetch origin pull/<PR编号>/head:<本地分支名>
    # 例如：git fetch origin pull/5/head:pr-5-review
    git checkout pr-5-review

用于在本地测试队友提交的 PR，不影响你自己的分支。


----------------------------------------------------------------
第三部分：两人合作流程规范（基于 TextRPG 项目场景）
----------------------------------------------------------------

【最小可执行流程】

    Issue → 分支 → commit → PR → 互相 review → CI 通过 → 合并 → Issue 关闭

下面用一个真实例子串起来：

══════════════════════════════════════════════════════════════
示例任务：修复 /help 指令的描述文字不准确的问题
══════════════════════════════════════════════════════════════

【角色分工】
  A 同学（负责人）：发现问题、创建 Issue、编写修复代码、提 PR。
  B 同学（审查者）：Review PR、测试验收、最终合并。

──────────────────────────────────────────────────────────────
步骤 1：A 同学 在 GitHub 网页端创建 Issue
──────────────────────────────────────────────────────────────
标题：  fix: /help 指令描述文字不准确
内容：
    ## 问题描述
    运行 /help 后，显示的背包指令说明写的是"查看物品"，
    应改为"查看背包中的物品列表"，措辞不够清晰。

    ## 复现步骤
    1. 启动游戏：python -m game.main
    2. 输入 /help
    3. 观察"背包"条目的描述

    ## 预期行为
    描述文字改为："查看背包中的物品列表"

    ## 验收标准
    - [ ] /help 输出中，背包指令描述已更新
    - [ ] pytest 全部通过
    - [ ] B 同学本地运行验证通过

创建后 Issue 会自动获得编号，例如 #7。

──────────────────────────────────────────────────────────────
步骤 2：A 同学 在本地创建分支并开发
──────────────────────────────────────────────────────────────
    git checkout main
    git pull origin main
    git checkout -b fix/help-inventory-description

修改对应文件（如 game/main.py 或 game/commands/ 下的文件），
把描述文字改正确。

修改完成后：
    git add .
    git commit -m "fix: 修正 /help 中背包指令的描述文字 (#7)"

（commit 信息末尾加 (#7) 可以让 commit 与 Issue 自动关联。）

    git push origin fix/help-inventory-description

──────────────────────────────────────────────────────────────
步骤 3：A 同学 在 GitHub 网页端提 PR
──────────────────────────────────────────────────────────────
- 推送后 GitHub 会弹出 "Compare & pull request" 按钮，点击。
- 标题：fix: 修正 /help 中背包指令的描述文字
- 描述：
    ## 改动内容
    修正 /help 指令输出中背包条目的描述文字。

    ## 关联 Issue
    Closes #7

    ## 测试方法
    1. python -m game.main
    2. 输入 /help，确认背包描述已更新
    3. pytest

- 在右侧 Reviewers 栏指定 B 同学为审查者。
- 点击 Create pull request。

──────────────────────────────────────────────────────────────
步骤 4：等待 CI 检查
──────────────────────────────────────────────────────────────
PR 创建后，CI 会自动运行（如果仓库配置了 GitHub Actions）。
在 PR 页面底部可以看到检查状态：
  ✅ 绿色表示通过，可以继续 review。
  ❌ 红色表示失败，A 同学需要修复后重新推送。

──────────────────────────────────────────────────────────────
步骤 5：B 同学 Review PR
──────────────────────────────────────────────────────────────
- 在 GitHub PR 页面点击 "Files changed" 查看改动。
- 对有疑问的行，点击行号左侧的 "+" 添加评论。
- 本地验证（可选但推荐）：
    git fetch origin pull/7/head:pr-7-review
    git checkout pr-7-review
    python -m game.main   # 手动输入 /help 检查

- 验收标准全部满足后，点击 "Review changes" → 选择 Approve
  → Submit review。
- 如有问题，选择 "Request changes" 并写清楚需要修改的内容。

──────────────────────────────────────────────────────────────
步骤 6：B 同学 合并 PR
──────────────────────────────────────────────────────────────
CI 通过 + B 同学 Approve 后：
- 点击 PR 页面的 "Merge pull request" → "Confirm merge"。
- 合并完成后可以点击 "Delete branch" 删除已合并的分支，保持仓库整洁。

──────────────────────────────────────────────────────────────
步骤 7：Issue 自动关闭
──────────────────────────────────────────────────────────────
因为 PR 描述里写了 "Closes #7"，合并后 Issue #7 会自动关闭。
如果没有写 Closes，需要手动去 Issue 页面点击 "Close issue"。

──────────────────────────────────────────────────────────────
两人协作注意事项
──────────────────────────────────────────────────────────────
1. 每项任务都从 Issue 开始，避免"我以为你在做"的沟通误解。
2. 分支名和 commit 信息要写清楚做了什么，不要用 "fix bug" 这样的模糊描述。
3. 不要直接向 main 分支推送代码；所有改动都通过 PR 合并。
4. PR 没有 Approve 之前不要自己合并。
5. 定期执行 git pull origin main 保持本地代码最新，减少冲突。
6. 遇到冲突不要独自硬解，截图给队友一起看，避免误删对方代码。
